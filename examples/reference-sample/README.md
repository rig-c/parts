# reference-sample

**A fixture, not on display.** Published as `sample` until issue #227, which
renamed it when the display examples became `demo` (repainted) and `scarf`; nothing
about it changed. Its `expected/` is the reference implementation's own output, and
its `config.json` keeps `"key": "sample"`, the key the reference named its skeleton
after (`sample_painting`, which `expected/` carries).

`expected/rig.json` is the flat form: every bone unturned, which is `flattenRig`
(`src/rig.ts`) of the built rig and the form the reference implementation wrote. A
build's `rig/rig.json` turns each chain link along its chain, so it carries `rotation`
and `length` on the links, and the offsets under them in the turned frame, where this
file holds unturned offsets only: a plain diff of the two shows those bones and the
weights bound to them as changed, and the build is not broken. The chain suite (`CH03`)
compares this file with `flattenRig(built)`, not with the built file; compare the same
way.


A generated full-body character — prompted as an adult woman with long wavy
hair in a cream blouse and a navy pinafore dress, standing with her hands
clasped in front of the waist — made to
be this repository's plain public fixture: base checkpoint, no LoRA, and a rig
the reference implementation built from its own proposal with no hand edit.
Its heavy inputs (the painting, the two images See-through was fed, and the
`full` and `head` See-through layer sets) live in the
[parts-examples](https://github.com/rig-c/parts-examples)
repository (as `reference-sample/`), which also holds the generation record and the licence;
`bun run fetch-examples` copies them into `inputs/` here (gitignored). What is
tracked is the light half: `config.json` (the reference's config converted to
this schema, `src/config.ts`), `proposal.json` (what the proposer wrote — the
`propose` stage — but for its first two notes, the head frame and pitch
this port adds, issue #250), and under `expected/` the reference implementation's outputs,
for the TypeScript stages to be compared against — `parts.json` (`assemble`;
its `visible_px`, `occluded_px` and `visible_not_projected_px`, and its
top-level `recomposite` block of uncovered holes, are this port's counts, which
the reference does not write, inserted from this port's own default build with
every reference value left as it was),
`rig.json` (the reference's, whose bones are all unturned; this port turns each chain link along its chain — issue #73 — so the built rig is compared through `flattenRig`, which turns every offset back, and matches it exactly), `motion.json` and `mesh_report.json` (`rig`), and `check.json` and
`gate_spine-html.txt` (`check`, the last being rig-c's gate lines); `check.json` is
regenerated by this port's `build`, because the reference has no judgement lines
— issue #11 — and again when the turned chains moved a judgement figure or two in
the third place through the runtime's float32 posing — issue #73 — and so is `motion.json`, whose blink holds 0.084 s where the
reference's held 0.04 s, less than one 12 fps frame — issue #32; its four hold-end
and open-end key times are the only values that differ from the reference's beyond the rounding of its float64 sums). Issue #119 (`assemble` clears a fringe below alpha 250 where the painting shows the part beneath it, which the reference did not) moved these from the reference's: `parts.json` holds this port's values for the 15 parts the rule touched — 276 px pushed back, each part's `fringe_pushed_back` list by holder, `opaque_px` and the three visibility counts taken after it, the boxes of `brow_r` (25 wide, was 27) and `iris_r` (19 wide, was 20), and `seam_override_px` one higher on `iris_r` — and this port's `recomposite` block (error px 4,359, was 4,512). `rig.json` holds this port's region offsets for `brow_r` and `iris_r` and this port's `hair_front` lattice (hull 56, was 54, with its uvs, weights and triangles), rebuilt on the 62 px the rule cleared from that part; `mesh_report.json` holds that mesh's hull and triangle count (200, was 202). `check.json` is this port's build of them (15 reported figures moved, every status as before). Issue #126 turned every mesh triangle counter-clockwise in Spine world, the winding rig-c reads a mesh in (the reference, and this port before it, wrote them clockwise there). The declared exception, and nothing else: every mesh `triangles` triple `[a, b, c]` is `[a, c, b]` in `rig.json`; the `check.json` `TEXTURE_STRETCH` entries that print a triangle's vertices and edge print them in that order (16 here, 52 over the three examples; the triangle, frame and figures are unchanged); and the untracked `skeleton.model.json`'s `spine.sha256`, which follows the skeleton bytes. Every rendered frame of the build is pixel-equal before and after. Issue #183 prepared this rig for a jiggle, and the config and these files carry it: two bones that are not the reference's, `chest_jiggle` (parent `chest`, at 419,320) and `hip_jiggle` (parent `hip`, at 419,520), each with a `physics` constraint (`bust_phys`, `hip_phys`) and no track of its own; `topwear` and `bottomwear` move from the lattice to contour mode (spacing their former grid, 18 and 28), because only a contour or automatic mesh carries a region, with a `circle` region on `chest_jiggle` (`bust`) and two on `hip_jiggle` (`hip_r`, `hip_l`). `rig.json` holds this port's bones, constraints and those two meshes (its other rows are as they were); `mesh_report.json` those two rows; `check.json` and `gate_spine-html.txt` are this port's build of it, whose loop line is read with the physics left out and whose `loop physics:` line names the two constraints. The idle keys `chest` and not `hip`, so in the idle the hip constraint moves nothing and the bust one moves its bone at most 0.066 rig px (idle frame 2): the constraints are there for a consumer's motion. `animations.json` is one such motion, and the public example of `motion.animations_from` (AUTHORING §3): a file in rig-c's motion-spec shape, named by the config, whose one animation, `hop` (1 s, not looped), keys only `hip`'s translate — a crouch to -5, a rise to +24 at 0.3 s, a landing at -6 at 0.45 s and a settle to 0 at 0.55 s — so `chest` follows through the hierarchy and nothing keys the jiggle bones. `build` writes it into `motion.json` after the idle, as read; `check` names it on its `beside the idle:` line, reads it for folds — `ANIMATIONS_DO_NOT_FOLD` (issue #320), rigc's `render --folds` with the two constraints left out, which reads no folding mesh; that key, after `TEXTURE_STRETCH`, is the only thing in `check.json` it moved — and measures the idle for every other bar. The two constraints are tuned for it (`bust_phys` inertia 0.25, strength 120, damping 0.92, mass 1; `hip_phys` inertia 0.2, strength 160, damping 0.88, mass 1.5): rendered at 30 fps, `hop` moves `chest_jiggle` at most 6.702 rig px and `hip_jiggle` at most 4.609 rig px from where keys alone put them (frame 14, at the landing), and they overshoot after it (3.27 and 1.35 rig px at frames 21 and 22); check's texture-stretch reading over those frames is 1.719 (`topwear`) and 1.602 (`bottomwear`) against its ceiling 1.926544. Those are rig-c 2.45.2's renders (issue #305: its physics clock no longer ends a frame on a step's tie); on rig-c 2.40.0 the same build read 6.583 and 4.432 (frame 13), 3.38 and 1.38, and 1.697 and 1.566, and `docs/evidence/sample-hop.png` shows that render's frames 14 to 21. Adding `hop` widened the render's fitted viewport, which the idle frames share, and moved `check.json`'s `torso_heat_mean` from 7.8 to 7.705 with every status as before; the new constraint values moved `topwear`'s smallest idle stretch ratio from 0.979 to 0.98. `motion.json` holds `hop` after the idle, `rig.json` the two constraints' values, and `gate_spine-html.txt` counts two animations. Issue #209 carried the seam's composite onto the render's pixel centres — the setup-pose still renders at frame scale 1.0116 here, not 1 — which moved `check.json`'s `seam_mean` from 0.208 to 0.204 and `seam_px_over_40` from 0 to 2 (one pair, `hair_back` / `neck`, under the bar of 50), with every other figure as before. Issue #216 judges the seam's pixel count in rig pixels — the frame count divided by s², so the bar reads one rig the same at every frame scale — and writes the scale it divides by as `check.json`'s `seam_frame_scale` (1.011614 here) after the three seam figures; that key is the only byte that moved, and the verdict is as before (2 frame px over 40, 1.95 rig px, against 50). Issue #333 reads the idle for folds with `hop` (`ANIMATIONS_DO_NOT_FOLD`): it folds no mesh, so `check.json`'s `animations` gains `"idle"` before `"hop"`, and nothing else in it or any other file moved. Issue #347 turns a sleeve's chain far (`STRESS_OFF_CHAIN`): this rig's one `sleeves` mesh rides both sleeve chains, so the line is not read and says why — `check.json` gains the key after `ANIMATIONS_DO_NOT_FOLD`, SKIP with that reason, and nothing else in it or any other file moved; the summary reads 10 of 11 bars, 1 skipped. `sheets/` holds the reference's
contact sheets of the two layer sets and of the assembled parts (`sheet`).

## What the README showed

Until issue #227 the README showed this character's contact sheet
(`assets/sample-parts.png`, still in the tree) as "the plain fixture: same
checkpoint, no LoRA, and a rig built from its own proposal with no hand edit at
all", with `check`'s seam line verbatim —
`seam: setup pose at 379x1216, scale 1.0116: mean |d| 0.204 (<= 1.0), 2 px over 40, 1.95 rig px (the count / s²; <= 50), 0 px over 80 (reported)`
— and loop max |d| 0.

## Pinholes at rest

Its flat parts stack holds four pinholes (issue #944; AUTHORING §7, *Pinholes at rest*), so it does not declare the bar and `assemble` prints `ASSEMBLE_PINHOLES: SKIP`: `481,437 2x6` (6 px) and `482,432 1x4` (4 px) on the seam line between `sleeves` and `topwear`, which no layer of either run holds — only the painting does — and `519,270 2x2` (3 px) and `514,267 2x1` (2 px) beside `hair_back`, whose pixels only the full run's `back hair` holds while the plan takes the head run's ([#956](https://github.com/rig-c/parts/issues/956)); they wait on [#953](https://github.com/rig-c/parts/issues/953).
